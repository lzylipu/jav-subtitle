# 🎬 NAS 日文字幕流水线

**简体中文** | [English](README_EN.md)

给自己的 NAS 做的一套**全自动日文影片 → 简中字幕**流水线。放进一个目录，网页上点两下，它自己一部一部把字幕做完。

- 不改动、不删除、不重命名原视频（只会在影片旁新建 `*.srt`，写入前有后缀白名单校验）
- 已有中文字幕自动跳过，不会覆盖
- 单文件处理：`片名.mkv` + `片名.zh-CN.srt`，同目录并列
- 适合**一次性几百到几千部**的长跑场景，崩了重启能续上
- **只用 CPU**：不做显卡加速（CTranslate2 没有 Intel/AMD 核显后端），N100 这类小主机直接跑

> 本项目**不包含任何 API 密钥**。翻译接口地址、模型、密钥全部在网页上填，只存在你本地数据库里。

## 🚀 部署：只改端口和路径

整个部署只需要改**两行**——端口和影片目录。其余（登录口令、数据库、模型目录、翻译接口、并发、限流）全部**首次运行自动创建**，之后在 Web UI 里配。

### 方式 A：拉现成镜像（不构建，最快）

```bash
mkdir -p /opt/jav-subtitle && cd /opt/jav-subtitle
curl -O https://raw.githubusercontent.com/lzylipu/jav-subtitle/main/compose.image.yaml
```

打开 `compose.image.yaml`，只改这两处：

```yaml
    ports:
      - "8000:8000"                 # ① 左边换成你要用的端口
    volumes:
      - /volume1/video:/media       # ② 左边换成你的影片目录
```

```bash
docker compose -f compose.image.yaml up -d
docker compose -f compose.image.yaml logs subtitle | grep -A6 首次启动
```

日志里会打印首次启动自动生成的登录口令（形如 `用户名：admin  密码：xxxxxxxx`），同时写进 `./data/account.json`（权限 600），重启不会变。

打开 `http://<NAS-IP>:<端口>/` 会跳到 `/login` 登录页（网页表单，不是浏览器原生弹窗），用户名固定 `admin`，填口令即可。登录态存在 HttpOnly Cookie 里，有效期 30 天，重启容器不掉登录；左侧栏底部「退出登录」可登出。改口令会让所有旧登录态立即失效。

| 仓库 | 地址 |
|---|---|
| Docker Hub（主） | `lzylipu/jav-subtitle:latest` |
| GHCR（镜像） | `ghcr.io/lzylipu/jav-subtitle:latest` |

### 方式 B：本地构建

```bash
git clone https://github.com/lzylipu/jav-subtitle.git
cd jav-subtitle
# 同样只改 compose.yaml 里的端口和路径
docker compose up -d --build
docker compose logs subtitle | grep -A6 首次启动
```

### 首次启动会自动创建什么

| 自动创建 | 位置 |
|---|---|
| 登录账号 | `./data/account.json`（`WEB_PASSWORD` 环境变量优先） |
| 数据库（全部设置、任务、翻译记忆） | `./data/pipeline.db` |
| whisper 模型 | `./data/models`（首次下 460MB） |
| 音频中间文件 | `./data/audio` |

想换口令：登录后进「设置 → 登录账号」改，改完当场生效（旧会话立即失效）。想彻底重来：停容器后删 `./data`。

首次启动会自动下载 whisper 模型（`small` 约 460MB），国内建议加环境变量 `HF_ENDPOINT=https://hf-mirror.com`。

## 📖 用法：索引 → 选目录 → 排队

界面只有三个页签：**库与任务**（上面媒体库、下面任务，各自滚动）、**日志**（任务进度流水）、**设置**（改完点保存就生效）。

### 1️⃣ 索引

点「库与任务」→「重新索引」。程序递归扫描 `MEDIA_DIR`，把每个视频记进索引表。
这一步只读元数据（`stat`），不打开视频文件，几百 GB 也很快。

### 2️⃣ 浏览

索引完目录会显示成一张表：

```
目录            视频   已完成   未处理   队列中
电影/            4       0        4        0
剧集/            6       0        6        0
```

点目录名进下一层，点「上一级」回去。计数是**递归**的——`电影/` 的 4 部包含它所有子目录里的片子。

### 3️⃣ 开跑

勾选一个或多个目录 → 点「加入队列」。也可以进入某个目录后不勾选直接点，表示处理当前目录。

- 「只处理前 N 部」填 0 = 全部，填 5 = 只把 5 部推进队列（**先拿几部试水**）
- 入队后任务按 `优先级 → 入队顺序` 一部一部往下跑，网页上能看到实时进度

> 手动点「加入队列」会**跳过**「文件已稳定 120 秒」的防抖闸门——你自己点的，说明文件已经拷完了。
> 定时扫描那条路仍然保留这个闸门，避免把还在拷贝的半截文件排队。

## ⚙️ 三个阶段怎么排队

```
索引 ──► 抽音频队列 ──► 转写队列 ──► 翻译队列 ──► 写 .zh-CN.srt
          (ffmpeg)      (whisper)     (OpenAI 兼容)
```

三个阶段**各自独立排队、各有自己的 worker**：

- 一条片子在做转写时，别的片子可以同时抽音频、同时翻译
- **单条片子内部严格顺序**，不会出现半截字幕
- 默认三个并发都是 `1`；跑顺了再往上加

为什么这么设计：

| 阶段 | 瓶颈 | 建议并发 |
|---|---|---|
| 抽音频 | 磁盘 IO | 1–2 |
| 转写 | **CPU**，占满所有核 | 1（4 核机器再往上不加吞吐） |
| 翻译 | **网络等待**，CPU 几乎不动 | 受上游限流约束，不是受机器约束 |

## 🌐 翻译渠道（四个可选）

设置页「翻译渠道」里切换，**保存后下一次领取任务就按新渠道跑**，不用重启容器。
右侧有「测试当前渠道」按钮，会真发一句日文过去，把译文或**上游返回的原话**显示出来——
排查 key 是否有效，看这个比猜快。

| 渠道 | 要不要密钥 | 说明 |
|---|---|---|
| **OpenAI 兼容接口** | 要 base_url + 模型 + key | 大模型翻译，质量最好，按你的站点计费。密钥只存数据库 |
| **谷歌翻译** | 不用 | 走 `translate-pa.googleapis.com`，一次提交一组句子、原样返回一组译文，不会乱序。内置公开 key 失效会自动去谷歌前端抓新的 |
| **必应翻译** | 不用 | 走 `edge.microsoft.com`，句子数组进、数组出，国内可直连 |
| **DeepL 官方 API** | 要 key | 免费档每月 50 万字符，key 以 `:fx` 结尾自动走 `api-free`，否则走 `api.deepl.com`。端点也能手填 |

两点实现细节，都是踩过的坑：

- **密钥会自动清洗**：从网页/聊天里粘贴常带上首尾空格、引号、甚至 `Bearer ` 前缀。
  带着这些字符发出去的 `Authorization` 头会被上游判成无效 token ——表现就是「在聊天软件里能用、到项目里 401」。
  保存时会自动去掉这些字符。
- **翻译记忆按渠道隔离**：换渠道不会命中别的引擎的缓存，机翻结果不会污染大模型的 TM。

想完全免费跑：渠道选 `必应` 或 `谷歌`，不填任何密钥，直接入队即可。

### 🛟 备用渠道：主渠道挂了自动切（v3.7）

一个 key 失效就让整库任务停在第一批，是踩过的真实事故。现在可以在
「翻译渠道 → 备用渠道」里填 `google,bing` 这样的串（留空 = 不启用）：

- **只有「整库都跑不动」的错才切**：鉴权失败（401/403）、额度用光（456）、完全没配置。
  偶发的网络错、429 限流、返回条数不符仍由原渠道自己重试——两个渠道来回抖只会更乱。
- **切过去就粘住**：死掉的渠道只撞一次，后续批次直接走备用，不重复浪费等待。
- **只播报一次**：任务日志里出现一行
  `渠道「DeepL 官方 API（需 key）」不可用，已自动切到「谷歌翻译」：…`，
  不会把日志页刷成一面墙。
- **翻译记忆跟着实际干活的渠道走**：备用渠道的机翻结果不会被写进主渠道的缓存，
  主渠道恢复后不会拿旧机翻结果糊弄过去。

推荐组合：主渠道 `deepl`（质量好） + 备用 `google,bing`（免密钥、秒回）。
这样 key 过期、额度用光、上游抽风时，任务照跑，只是译文风格会变——日志里写明了原因。

## 🚦 限流：怎么保证不打爆中转站

这是 v3 的重点。有三个叠加的闸门：

1. **固定间隔发车**（`translate_min_interval`，默认 3 秒）
   任意两次翻译请求之间至少隔这么久。不是令牌桶——令牌桶允许攒满后一次性花掉（突发），固定间隔不允许。

2. **每分钟上限**（`translate_rpm`，默认 20）
   换算成间隔 `60/20 = 3` 秒，和上一条取较大值。

3. **429 全局冷却**（`translate_429_backoff`，默认 120 秒）
   一旦收到 429，**所有 worker 一起停手**（不是各自轮流去撞墙），冷却时间优先听上游的 `Retry-After`；连续 429 会翻倍，上限 30 分钟。冷却结束后自动续跑，任务不记为失败。

网页顶部有 `近1分钟请求` 和 `限流冷却` 两个标签，随时能看到限流器状态。

## 💰 成本控制

- **翻译记忆（TM）**：每句台词按 `模型+原文` 哈希入库，重复台词直接复用，**不再计费**。系列片的固定台词、片头片尾几乎全免费。
- **每日字数预算** `daily_char_budget`：当天送去翻译的字数超了，只停翻译阶段，转写照跑，第二天自动继续。0 = 不限。
- **失败不无限重试**：单阶段最多 3 次，退避 30/60/120 秒；密钥错误、模型不存在直接判死，不浪费次数。
- **断点续翻**：每批翻译完成立刻进 TM，重跑那批 0 成本。
- **卡住时能看见原因**：状态栏会显示「翻译接口最近一次报错」，日志页记录每一批失败的范围和原因（以前只显示进度不动，看不出在干什么）。
- **个别句子翻不过不拖累整部片**：整批不合格会拆成两小批重试（最多拆两层），再不行就逐条抢救；实在救不回来的几条保留日文原文，任务照样完成，日志里会写明有几条。
- 默认「每批几条字幕一起发」= **40**。同一批 120 条真实字幕实测：40 条一批 **2.6 秒/条**，20 条一批 **5.8 秒/条**——上游每次请求本身就要几十秒，批越小越亏。条数对不上时引擎会自动拆成两小批重发，不用靠小批次兜底。

## 🔌 AI 接入（给内网 Agent 用）

设置页最下面的「AI 接入（给内网其它 Agent 用）」分组里有现成控制面：

- 服务首次启动随机生成 `hs_...` 形式的 token，**只存在数据库**，网页可见可复制可重置
- 请求头用 `Authorization: Bearer <token>`，浏览器仍走 Basic 登录，两套并存
- 勾选「只读」后，这个 token 只能查询，不能暂停/重试/入队

典型用法：把这个地址和 token 丢给内网的 AI，它就能自己盯着队列、看日志、发现卡住就暂停。

```bash
# 一屏快照：计数 + 运行中 + 失败 + 最近日志 + 限流状态
curl -H "Authorization: Bearer hs_xxx" http://10.10.0.5:8000/api/ai/overview

# 完整接口清单
curl -H "Authorization: Bearer hs_xxx" http://10.10.0.5:8000/api/ai/help

# 全局日志
curl -H "Authorization: Bearer hs_xxx" "http://10.10.0.5:8000/api/logs?limit=100"

# 暂停队列
curl -X POST -H "Authorization: Bearer hs_xxx" \
     -H "Content-Type: application/json" \
     -d '{"reason":"磁盘要满了"}' http://10.10.0.5:8000/api/queue/pause
```

主要接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/ai/overview` | 一屏状态快照 |
| GET | `/api/ai/help` | 自描述接口清单 |
| GET | `/api/stats` | 计数、转写速度、剩余时间估算 |
| GET | `/api/library?path=` | 按目录看视频数量与进度 |
| POST | `/api/enqueue` | 目录入队 `{path, limit}` |
| POST | `/api/scan` | 重新索引 |
| GET | `/api/jobs?...` | 任务分页列表 |
| GET | `/api/jobs/{id}/events` | 单任务日志 |
| POST | `/api/jobs/{id}/retry` | 重试单个 |
| POST | `/api/jobs/retry-all` → `/api/jobs/retry-failed` | 重试全部失败 |
| POST | `/api/queue/pause` / `resume` | 暂停 / 恢复 |
| GET | `/api/logs` | 全局日志 |

## 🖥 硬件要求：只用 CPU

转写固定跑在 CPU 上，模型精度固定 `int8`。设置页「转写」那行字会显示实际线程数：

```
固定使用 CPU，精度 int8 ｜ 线程 4 ｜ 机器 8 线程
```

**为什么不支持显卡**：faster-whisper 底下是 CTranslate2，它官方只提供三种后端——CPU、NVIDIA CUDA、AMD ROCm，**没有 Intel GPU 后端**。也就是说：

| 硬件 | 本程序 |
|---|---|
| 任意 x86 CPU（含 N100 / N305 / E3 这类） | ✅ 能跑，就是 CPU 硬算 |
| Intel 核显（N100 的 UHD 核显、Arc） | ❌ 用不上 |
| AMD 核显 | ❌ 用不上 |
| NVIDIA 独立显卡 | 技术上能走 CUDA，但为了让项目保持精简，**不接** |

要让 Intel 核显跑 whisper，得把整个转写引擎换成 OpenVINO 版——另一套代码，镜像从 1.1GB 涨到 5GB 以上，而参考实测里连 Intel Arc 独显用 OpenVINO 也只比纯 CPU 快 1.3 倍（编码器还得留在 CPU）。为了这点收益把项目搞得又大又复杂并不值当，所以明确选择：**只做 CPU，镜像是纯 CPU 镜像，不带任何 CUDA 库**。

### CPU 上的现实

| 项 | 说明 |
|---|---|
| 模型 | `small` + `int8` 是 4 核机器的合理选择；`medium` 大概慢 2.5–3 倍 |
| 转写速度 | 参考实测：2 vCPU 上 5× 实时；4 核 8 线程预计 10–18× 实时（**需真机实测**） |
| 内存 | `small`+int8 单实例约 500MB–1GB，转写并发开 2 就要翻倍 |
| 线程数 | 默认自动（`min(4, 核数)`）；想手动压就填具体数字，0 表示自动 |
| 批推理 | 默认关。实测只快 34%，却会把 30 句并成 5 条 35 秒长字幕，**时间轴毁了** |
| 厚度 | 一部 90 分钟片：转写约 5–9 分钟，翻译取决于接口 |

真机上一条命令就能量出准数：

```bash
docker compose exec subtitle python tools/bench.py /media/某部片.mp4
```

## ⚠️ 已知限制

1. **只认日语对白**，唱歌、背景人声、方言口音会明显掉准确率
2. 模型是 `small`，台词密度高、语速快的片子会漏句；要更准换 `medium`，代价是 2.5–3 倍时间
3. 翻译质量取决于你接的模型，本项目只保证结构合法与顺序对齐
4. 时间轴来自 whisper 的 VAD 分段，不做二次对齐；长句会偏高
5. 单机单进程设计，没有分布式；5000 部以上建议按年份拆多个实例

## 📄 许可

自用项目，随你喜欢。
